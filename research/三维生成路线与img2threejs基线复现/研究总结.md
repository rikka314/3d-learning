# 三维生成路线与 img2threejs 基线复现

归档日期：2026-08-27

## 研究起点

最初问题是评估三条“coding agent 驱动三维内容生成”路线：

1. coding agent + Three.js；
2. coding agent + Blender MCP；
3. coding agent + UE5 MCP。

目标不是只比较理论能力，而是寻找成熟开源项目进行本地复现，并据此判断哪条路线在项目初期能最快呈现有说服力的视觉结果。研究随后收敛为第一个可执行任务：先在 Windows 工作区复现 `img2threejs`，建立 Three.js 路线的基线。

本阶段没有实际复现 Blender MCP 或 UE5 MCP，因此不能据此宣布三条路线的最终优胜者。当前可靠结论只覆盖 img2threejs 的工程可运行性、官方样例表现和后续评测方法。

## 三条路线的工作定义

以下是用于组织后续实验的定义，不是已经完成的对比结果。

| 路线 | Agent 的主要产物 | 典型优势 | 主要风险 |
| --- | --- | --- | --- |
| Three.js | TypeScript/JavaScript 程序化几何、材质与交互代码 | 迭代快、结果天然可部署到 Web、代码可审阅 | 复杂有机建模和高质量资产制作成本高 |
| Blender MCP | 通过 MCP 操作 Blender 场景、网格、材质、几何节点和渲染 | DCC 能力完整、资产格式成熟、适合继续人工编辑 | GUI/状态同步、插件稳定性和自动化闭环复杂 |
| UE5 MCP | 通过 MCP 操作 Unreal 项目、Actor、材质、蓝图和关卡 | 实时渲染上限高、适合交互场景和最终演示 | 环境重、启动和验证慢、项目状态面更大 |

## 已验证事实

### 1. img2threejs 的真实产品形态

img2threejs 不是传统的“上传图片，一次模型推理直接得到 3D 文件”。其上游将自己定义为供 coding agent 执行的分阶段工作流：

```text
参考图分析
  → 结构与细节清单
  → sculpt spec
  → Three.js 程序化模型工厂
  → 浏览器渲染
  → 视觉门禁与迭代修正
```

因此它的能力上限不仅取决于脚本，也取决于 agent 的视觉理解、spec 编写、代码修改和多轮复核质量。完整工作流入口见 [upstream/SKILL.md](../../reproductions/agent-3dgeneration/img2threejs/upstream/SKILL.md)。

### 4. 上游原样测试存在 Windows 启动兼容问题

首轮测试的失败集中在环境启动方式，而不是生成器逻辑：

- 上游 Python 测试直接调用 `npx`，Windows 实际入口为 `npx.cmd`；
- 上游直接执行 `node_modules/.bin/esbuild`，Windows 应执行 `esbuild.cmd`；
- 少数测试硬编码了相邻目录名 `img2threejs-showcase`，没有使用已经提供的环境变量。

本地只对 `upstream/forge/tests/` 做了 12 个文件的兼容修改：按平台解析 `npx`/Node package binary，并统一通过 `IMG2THREEJS_SHOWCASE_ROOT` 查找 showcase。生产生成器、intake/spec/review 流程和 showcase 模型代码均未改动。详见 [LOCAL_PATCHES.md](../../reproductions/agent-3dgeneration/img2threejs/LOCAL_PATCHES.md)。

## 结果解释

### 观察到的事实

官方 Crown Chest showcase 在本机可稳定构建和渲染，说明“程序化 Three.js 模型 + WebGL 展示”这条工程链路确实可复现。样例具有清晰的主体轮廓、分层结构、金属与珐琅材质区分、发光皇冠图案和可交互部件展示。

### 合理推断

img2threejs 很适合把风格化、硬表面、组件边界明确的物体快速变成可部署 Web 资产。它的初期演示效果可能优于从零搭建一般 Three.js 场景，因为上游已经提供了 spec、生成器、质量门禁和成熟 showcase 结构。

该推断尚未由统一的新输入实验验证。官方 showcase 是经过作者选择和打磨的样例，不能直接代表 coding agent 面对任意新图片时的平均成功率。

### 当前决策

将本次结果作为 Three.js 路线的“官方基线”，而不是独立生成能力的最终评分。当前不对 Blender MCP 和 UE5 MCP 作胜负判断。

下一阶段应该用同一张自有参考图、同一时间预算和同一验收标准，分别运行三条路线。只有这样才能回答“哪一种方法初期表现最好”。

## 建议的公平对比实验

### 输入控制

首轮选择一个单主体、背景干净、遮挡较少的 3/4 视角风格化硬表面物体，例如宝箱、台灯、玩具车或小型机器。建议分辨率至少 `512×512`。

三条路线必须共享：

- 同一张参考图；
- 同一文字目标；
- 同一总时间预算；
- 同一 agent 模型与推理级别，或明确记录差异；
- 同一人工介入次数上限；
- 同一输出视角和灯光规范。

### 建议指标

| 指标 | 建议权重 | 测量方法 |
| --- | ---: | --- |
| 轮廓与比例相似度 | 25% | 固定视角 silhouette IoU、包围盒比例差 |
| 关键部件完整度 | 20% | 预先列出的 feature checklist |
| 材质与颜色观感 | 15% | 固定灯光截图人工盲评或颜色差 |
| 首个可看结果耗时 | 15% | 从任务开始到可渲染结果 |
| 可编辑性 | 10% | 部件命名、层级、参数化程度 |
| 交互/部署成本 | 10% | Web、Blender、UE5 中继续使用的步骤 |
| 稳定性 | 5% | 失败、重试和人工修复次数 |

除最终总分外，还应分别记录“10 分钟首屏效果”和“60 分钟优化效果”。初期表现往往由首屏速度决定，而最终上限更受工具深度影响，两者不应混为一个结论。

## 尚未完成与风险

- 尚未对一张新的自有图片完整执行 img2threejs 的 agent 分析、spec 编写、生成和多轮视觉修正。
- 尚未锁定并复现 Blender MCP 的候选开源项目。
- 尚未锁定并复现 UE5 MCP 的候选开源项目。
- showcase 固定快照中未发现独立 `LICENSE` 文件；对外分发或商用前需再次确认许可和素材授权。
- Vite 构建成功但部分 bundle 很大，官方展示适合作为能力样例，不代表已经完成生产性能优化。
- img2threejs 的结果质量与 coding agent 的视觉推理和迭代质量强相关，不能只把它当成确定性 CLI 生成器评估。

## 下一步建议

1. 选定一张统一的自有参考图，先完成 img2threejs 从新输入到新模型的完整闭环。
2. 为 Blender MCP 和 UE5 MCP 分别筛选一个仍在维护、许可清楚、可脚本化复现的项目并锁定提交。
3. 建立统一目录、计时方法、截图视角和评分表。
4. 先比较 10 分钟首屏结果，再比较 60 分钟优化结果。
5. 将每条路线的日志、失败原因、人工介入和最终资产一起归档，避免只凭最佳截图判断。
